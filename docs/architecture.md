# アーキテクチャ設計書

## 設計の前提

[要件定義書](product-requirements.md)の1時間MVP、固定データ、単一画面、NFR-02・NFR-05の外部サービス非依存を基準とする。2026-09-13に以下の静的構成で実装した。実測結果は[実装検証記録](implementation-validation.md)を参照。

差し替え後の要件では特定フレームワークの指定がない。HTML・CSS・JavaScriptのみの静的フロントエンドを採用した。必要な業務処理が固定シナリオに収まり、ビルド工程が不要なため。

## 構成と責務

- `index.html`：1画面の構造、予定・予測・車両・操作の表示領域。Shouldを採用した場合は需要・ログ領域も持つ。
- `styles.css`：模式図上の車両位置、領域の配置、状態の視覚表現、レスポンシブ表示と移動演出。街の道路・建物はHTML内のローカルSVG。
- `demo-data.js`：利用者、予定、車両、予測の加点、デモ時刻・ログ等の固定シナリオ。
- `demo-state.js`：純粋な状態遷移、確率判定、割り当て条件、ログ追加、演出完了状態。DOMから分離し、ブラウザーとNode.jsテストで同じ処理を使用する。
- `app.js`：イベント受付、表示更新、自動遷移のタイマー、移動演出とその完了処理。

以上は実装済みのファイル。テストと記録を含む配置は[リポジトリ構造](repository-structure.md)を参照する。

依存方向は、HTMLがCSS・固定データ・アプリ処理を読み込み、アプリ処理が固定データから現在の状態を作り、状態から画面を描画する向きとする。固定データからDOMやアプリ処理を参照しない。

UIの表示文字列を読み取って状態を判定しない。`demoPhase`を遷移の基準とし、`prediction.status`・`vehicle.status`・`assignedUserId`との不変条件を1か所で保つ。DOM操作、同じ確率計算、イベント登録を複数の場所に分散させない。

## 技術選択

### 静的なHTML・CSS・JavaScript

- 状態：採用済み。実行時の依存パッケージ・フレームワーク設定なし。
- 理由：データの入出力が固定で、必要な業務遷移が5つ、操作が3つ。バックエンドやビルド工程を必要としない設計にできる。
- 代償：画面や共有部品が増える段階では、DOM更新の整理やコンポーネント化を再検討する必要がある。
- バージョン：依存パッケージを導入する前提がなく、パッケージのバージョンは未設定。検証対象ブラウザーの版は実装時に記録する。

### ローカルファイルからの実行

`index.html`をブラウザーで直接開ける構成を採用。JavaScriptは `demo-data.js → demo-state.js → app.js` の順に通常のdeferスクリプトとして読み込む。`fetch`によるデータ読込、モジュールの取得、CDN、外部フォント・画像に依存しない。街・アイコンはHTML内のSVGとCSSで描画する。

Chrome・Edgeでネットワークを無効化した新規ブラウザーコンテキストからfile://起動と全操作を検証。起動方法は[README](../README.md)に記載する。静的配信も可能だが、サーバーはアプリの必須構成ではない。

### メモリー内の状態

保存先はブラウザー上のメモリーだけとし、DB・localStorage・Cookie・セッション復元は使わない。再読み込みで必ず初期値から生成する（NFR-03）。すべて架空のデータで、端末の位置・カレンダー・履歴を取得しない。

## 状態処理とデータ境界

`INITIAL → PREDICTED → POSITIONING → CONFIRMED → ASSIGNED` の順序を固定する。PREDICTEDからPOSITIONINGへの自動遷移をアプリ処理が担当する。利用者の3操作と自動遷移を同じ状態検証に通し、不正順序を受け付けない。

需要ステータスは百分率から判定する。82%はPOSITIONING条件であり、車両の専用割り当て条件ではない。Vehicle-03の割り当て先を設定できるのは、CONFIRMEDからASSIGNEDに進む処理だけとする（AC-04・AC-07）。

車両のモデル上の目標位置とアニメーション途中の描画座標を分離する。CSSの完了イベントだけに進行を依存させず、演出を省略する経路でも到着後の処理を呼ぶ。補完案として完了処理を重複実行しても結果が変わらない形にし、演出時間に対応したフォールバックを用意する。

予約の1.00と予測の0.82は予測配置時点の需要集計。Shouldを実装する場合、現在確率98%とは別のスナップショットとして扱う。詳細は[機能設計書](functional-design.md)に従う。

## 品質と検証方針

- NFR-01：状態計算はローカルで行い、外部応答を待たない。実機で操作からUI変化開始までが1秒以内か確認する。演出完了はShouldの1〜2秒という別条件。
- NFR-02・NFR-05：必要なファイルをローカルに揃え、ネットワークを無効にして全シナリオを再生する。APIキー、通信、権限ダイアログが不要であることを確認する。
- NFR-03：タイマー・ログ・割り当てを含め、再読み込み後にINITIALから始まることを確認する。
- NFR-04：82%の周辺配置と98%後の確定割り当てを、位置と文字で区別する。審査員役による約30秒の説明確認を行う。

具体的な受け入れ確認は[開発ガイドライン](development-guidelines.md)、実行結果は[実装検証記録](implementation-validation.md)に集約する。初見の審査員役による理解容易性の確認は未実施。

## 将来構想の境界

要件第36〜38章の構想は保持するが、今回のコードをサービスやエージェントに分割する理由にはしない。

- User Agent：カレンダー・履歴・到着希望・歩行可能距離・アクセシビリティから利用者需要を把握する構想。
- Vehicle Agent：位置・空席・次回予約・走行状態・到着可能時間を管理する構想。
- City Agent：道路・渋滞・工事・停車場所・一時乗降場所を扱う構想。
- 将来の協調は、需要推定・車両可用性・街の制約を合わせて周辺配置を決める。MVPでは固定ログ等で説明し、実際のメッセージ通信は実装しない。
- プライバシーモードはSTANDARD・LIMITED・PRIVATE・OFFの構想を残す。設定画面、同意管理、実データの保存方式は今回設計しない。
